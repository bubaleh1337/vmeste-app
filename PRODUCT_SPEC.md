# «Копим вместе»: спецификация приложения для совместных накоплений

Версия: 0.2  
Дата: 31 августа 2026 года  
Локализованное рабочее название — «Копим вместе» на русском и Saving Together на английском. Оба варианта меняются через настройки окружения.

## 1. Назначение

Приложение помогает двум или нескольким людям совместно копить на цель, видеть фактический прогресс и отдельно анализировать расходы, чтобы понимать, сколько ещё можно было бы отложить.

Основной тестовый сценарий: Катя и Никита копят на квартиру к 01.04.2027. Они вручную добавляют вложения на депозиты или импортируют операции из CSV/XLSX, видят общий результат, вклад каждого, расходы по категориям и прогноз достижения цели.

## 2. Неприкосновенные правила продукта

1. Накопления и расходы — независимые контуры.
2. Расход никогда не уменьшает накопленную сумму.
3. Прогресс меняют только операции накоплений: пополнение, проценты, снятие, комиссия и корректировка.
4. Участники видят общие данные и могут добавлять и редактировать операции.
5. Только владелец управляет участниками и архивирует или удаляет цель.
6. Существенные изменения сохраняются в журнале: автор, время, прежнее и новое значение.
7. Деньги не хранятся и не вычисляются через `float`.
8. Импорт создаёт операции только после предварительного просмотра и подтверждения.
9. Приложение не подключается к банку и не запрашивает банковские логины или пароли.
10. Интерфейс спокойный и эстетичный, без ощущения бухгалтерской программы.

## 4. Роли

### Владелец

Может редактировать цель и операции, создавать и отзывать приглашения, удалять участников, архивировать цель и инициировать её удаление.

### Участник

Может просматривать общие данные, редактировать параметры цели, добавлять, редактировать и мягко удалять операции, импортировать CSV/XLSX и смотреть журнал действий.

Не может управлять участниками, передавать владение, архивировать или удалять цель и физически стирать финансовую историю.

### Общие ограничения

- В MVP у цели один владелец.
- Один пользователь может состоять в нескольких целях.
- Удалённый участник теряет доступ, но его прежние операции и авторство сохраняются.
- Архивная цель доступна только для чтения.
- Расходы внутри совместной цели видны всем её участникам; это явно показывается до первого импорта.

## 5. Вход и приглашения

### OAuth

- Первый реальный провайдер — Google через Supabase Auth.
- Apple обязателен перед полноценным публичным релизом, но не блокирует прототип.
- Приложение не создаёт и не хранит собственные пароли.
- После первого входа пользователь выбирает отображаемое имя.
- Связывание подтверждённых OAuth-идентичностей выполняется безопасными средствами провайдера Auth.

Apple может выдать скрытый relay-email. Поэтому доступ нельзя предоставлять только по совпадению email. Для веб-OAuth Apple также нужен отдельный developer setup и регулярная ротация секретного ключа.

### Сценарий приглашения

1. Владелец нажимает «Пригласить участника».
2. Приложение создаёт одноразовую защищённую ссылку.
3. Владелец отправляет её удобным способом.
4. Получатель открывает ссылку и входит через доступный OAuth.
5. Токен связывает вошедшего пользователя с целью независимо от email провайдера.

Правила:

- в базе хранится только хеш токена;
- срок действия — 7 дней;
- ссылка одноразовая и может быть отозвана;
- повторное принятие не создаёт дубль;
- архивная/удалённая цель не принимает приглашения;
- отправка email самим приложением не входит в первый этап: сначала копирование ссылки.

## 6. Накопления

### Типы операций

Вводимая сумма всегда положительна, направление задаёт тип.

| Тип | Баланс | Значение |
| --- | ---: | --- |
| `contribution` | + | Взнос на депозит |
| `interest` | + | Проценты банка |
| `withdrawal` | − | Снятие |
| `fee` | − | Комиссия депозитного счёта |
| `adjustment_plus` | + | Положительная корректировка |
| `adjustment_minus` | − | Отрицательная корректировка |

`actual_saved = contributions + interest + adjustment_plus − withdrawals − fees − adjustment_minus`

Правила:

- начальный остаток создаётся как аудируемая положительная корректировка;
- автор записи и участник, которому принадлежит вклад, могут различаться;
- `created_by` неизменяем;
- для корректировки обязателен комментарий;
- расход не входит в формулу;
- нормальное снятие/комиссия не должны уводить баланс ниже нуля;
- отрицательная корректировка ниже нуля требует отдельного подтверждения;
- после первой финансовой операции валюта цели блокируется.

### Прогресс

- `progress_percent = actual_saved / target_amount × 100`;
- при отрицательном балансе визуальный прогресс равен 0%;
- числовой процент может превышать 100%;
- полоска заполняется максимум до 100%, превышение показывается подписью;
- `remaining = max(target_amount − actual_saved, 0)`;
- цель достигнута при `actual_saved >= target_amount`.

### Темп и прогноз

- оставшиеся дни считаются от локальной даты пользователя;
- `required_daily = remaining / days_remaining`;
- `required_monthly_average = required_daily × 30.4375`;
- при истёкшем сроке показывается нехватка без деления на ноль;
- прогнозируемая дата строится только при достаточной истории положительных чистых накоплений;
- прогноз явно называется оценкой.

### Вклад участников

`participant_net = его пополнения + закреплённые проценты/положительные корректировки − закреплённые снятия/комиссии/отрицательные корректировки`

Показываются сумма и доля каждого, последние пополнения и общий результат. Не использовать рейтинг и соревновательное давление.

## 7. Расходы

### Основное правило

Расходы нужны только для аналитики и никогда не влияют на накопления.

### Поля

- дата, сумма и валюта;
- исходное описание и нормализованный продавец;
- категория;
- кто потратил и кто добавил;
- источник: manual, csv, xlsx;
- признак «можно было избежать»;
- статус аналитики: included, excluded, needs_review;
- комментарий, даты изменений и мягкого удаления.

### «Можно было отложить»

`potential_savings = сумма расходов, явно отмеченных как необязательные`

- категория может предлагать значение по умолчанию;
- пользователь меняет его для любой операции;
- рядом пояснение: «Рассчитано по расходам, отмеченным как необязательные»;
- обязательные расходы не включаются.

### Переводы и возвраты

- перевод между собственными счетами не является расходом;
- возврат уменьшает расходы, но не накопления;
- снятие наличных попадает в `needs_review`, а не в расходы автоматически;
- импортированную строку можно исключить из аналитики без стирания записи импорта.

### Категории по умолчанию

Продукты; кафе и рестораны; транспорт; жильё и коммунальные услуги; здоровье и аптеки; красота и уход; одежда и покупки; подписки и связь; развлечения; образование; путешествия; питомцы; подарки и помощь; налоги и комиссии; переводы; наличные; другое; требует проверки.

Можно создавать категории и менять цвет/иконку. Системная категория не удаляется физически, пока на неё ссылаются операции.

### Категоризация

Пример: описание содержит `MAGNUM` → «Продукты».

- порядок: точные пользовательские правила → локальный встроенный словарь → `needs_review`;
- при конфликте побеждает более конкретное правило;
- результат всегда редактируем;
- после ручной смены категории можно предложить сохранить правило;
- банковские строки не отправляются внешнему ИИ.

## 8. Дашборды

### Обзор цели

- название, срок, сумма и цель;
- процент и крупная полоса прогресса;
- остаток и необходимая средняя сумма в месяц;
- оценочная дата достижения;
- участники и вклад каждого;
- изменение накоплений по месяцам;
- последние действия;
- кнопки «Добавить накопление», «Добавить расход», «Импортировать».

### Расходы

Фильтры: период, участник, категория, источник.

Элементы:

- всего потрачено;
- обязательные и необязательные расходы;
- «Можно было отложить»;
- кольцевая диаграмма категорий;
- сравнение месяцев;
- крупные категории;
- список категорий с суммой и долей;
- операции `needs_review`;
- переход в отфильтрованный список из диаграммы/категории.

Диаграммы имеют текстовые значения и не передают смысл только цветом.

## 9. Импорт PDF/CSV/XLSX

### Сценарий

1. Выбор назначения: расходы или накопления.
2. Загрузка `.pdf`/`.csv`/`.xlsx`.
3. Выбор листа XLSX и строки заголовков.
4. Сопоставление столбцов.
5. Выбор формата даты, десятичного разделителя и кодировки CSV при необходимости.
6. Preview.
7. Проверка категорий, типов, переводов и дублей.
8. Подтверждение выбранных строк.
9. Атомарное создание операций.

Поддерживаются: один столбец суммы со знаком, отдельные дебет/кредит или сумма плюс тип. Обязательны дата, описание и сумма либо дебет/кредит.

### Безопасность импорта

- файл по возможности разбирается в браузере;
- оригинал не сохраняется по умолчанию;
- в базе остаются подтверждённые нормализованные данные и метаданные импорта;
- SHA-256 файла предупреждает о повторной загрузке;
- номера карт/счетов маскируются в preview и логах;
- есть лимит размера и строк;
- формулы и макросы не выполняются, читаются только сохранённые значения;
- критическая ошибка откатывает весь commit.

### Дубли

Защита многоуровневая и не зависит от конкретного банка:

1. SHA-256 блокирует повтор точно того же файла.
2. Если банк отдаёт стабильный `transaction/reference ID`, он используется как основной идентификатор.
3. Если ID нет, используется content fingerprint: `goal + дата + сумма + валюта + debit/credit + нормализованное банковское описание`.
4. Если удаётся определить счёт/IBAN/маску карты, fingerprint дополнительно ограничивается SHA-256 отпечатком счёта; исходный номер счёта не сохраняется.
5. Для одинаковых операций используется count-based reconciliation: если в старой выписке было две одинаковые операции, а в новой три, импортируется только третья.
6. Банк может быть неизвестен приложению: generic fallback всё равно работает по содержимому операции.

Категория, участник и классификация `проценты/пополнение` не являются частью банковской идентичности операции, поэтому их ручное изменение не должно создавать повтор при следующем импорте.

## 10. Экраны и навигация

Публичные: лендинг, OAuth, callback, принятие приглашения, конфиденциальность и условия.

Авторизованные: «Мои цели», создание, обзор, накопления, расходы, импорт, участники, аудит, настройки цели, профиль/экспорт/удаление аккаунта.

- мобильная навигация: «Обзор», «Накопления», «Расходы», «Ещё»;

- основное действие доступно максимум за два нажатия;
- критическое удаление находится отдельно от ежедневных действий.

## 13. RLS и безопасность

- RLS включена на каждой API-таблице;
- цель читают только активные участники;
- активные участники изменяют операции своей цели;
- `created_by`, `goal_id` и исходное авторство нельзя подменить;
- только владелец меняет участников, приглашения и статус цели;
- участник не назначает себя владельцем;
- приглашение принимается атомарной серверной функцией по токену;
- `service_role` никогда не попадает в браузер;
- удалённые строки скрыты из обычных расчётов, но доступны аудиту/восстановлению;
- RLS тестируется для владельца, участника и постороннего пользователя;
- HTTPS и allowlist redirect URL в production;
- секреты только в environment variables, не в Git;
- серверная сессия использует безопасные cookie;
- rate limit на приглашения;
- входные данные проверяются Zod на границе;
- реальные выписки не используются в fixtures, тестах, скриншотах и логах;
- error logs не содержат банковских описаний и OAuth-токенов;
- до публичного релиза нужны экспорт, удаление аккаунта, privacy policy и terms.

- Vercel или совместимый хостинг после локальной проверки.

В MVP не добавлять ORM поверх Supabase без доказанной необходимости. UI обращается к типизированным репозиториям/сервисам, а не к сырым таблицам.

### Планируемая структура

```text
src/
  app/                # public, auth и app routes
  components/         # ui, charts, forms, layout
  features/           # auth, goals, savings, expenses, imports, members, audit
  lib/                # money, dates, validation, supabase
  server/             # repositories, services
  styles/
  test/
supabase/             # migrations, seed
tests/e2e/
public/
docs/
```

- бизнес-формулы не находятся в React-компонентах;
- денежные функции чистые и покрыты unit-тестами;
- импорт разделён на parse, normalize, validate, deduplicate, commit;
- demo/mock доступен только в development и не может включиться в production.

## 15. Доступность и локализация

- интерфейс полностью поддерживает русский и английский; выбранный язык хранится в профиле и дублируется локальной cookie для публичных страниц;
- локаль дат/чисел отделена от валюты;
- клавиатура работает для форм, диалогов и импорта;
- видимый focus state;
- доступные названия элементов и связанные ошибки полей;
- WCAG AA;
- текстовая альтернатива диаграмм;
- пустое состояние объясняет следующее действие.

## 16. Обязательные тесты

### Unit

- влияние всех типов накопительных операций;
- расход не меняет накопления;
- прогресс 0%, 100%, >100% и отрицательный баланс;
- истёкший срок без деления на ноль;
- точность minor units;
- potential savings только из discretionary;
- стабильный fingerprint дубля.

### Интеграционные/RLS

- владелец создаёт цель;
- участник принимает приглашение и редактирует операции;
- участник не удаляет/архивирует цель даже прямым запросом;
- посторонний не читает данные;
- импорт атомарен;
- soft delete меняет расчёты, но не стирает аудит.

### E2E

- OAuth → цель → начальная сумма → дашборд;
- приглашение → второй пользователь → совместное изменение;
- расход → диаграмма без изменения прогресса;
- CSV/XLSX → mapping → preview → commit → защита от дубля;
- ширина 390 px и 1440 px;
- loading, empty и error states.

## 17. Этапы разработки

### 0. Основа

Репозиторий, документы, Next.js, типы, lint/format/test, `.env.example`, design tokens.

### 3. Импорт

CSV, XLSX, mapping, preview, категоризация, дубли, атомарный commit.

### 4. Закрытый тест

Экспорт/удаление, privacy, безопасный мониторинг, accessibility review, тест двух пользователей, резервное копирование и восстановление.

### 5. Публичный релиз

## 18. Definition of Done для MVP

1. Два пользователя через OAuth работают с общей целью.
2. Посторонний не видит данные.
3. Только владелец архивирует/удаляет цель.
4. Прогресс зависит только от накопительных операций.
5. Расходы разложены по категориям и не меняют прогресс.
6. «Можно было отложить» использует только явно отмеченные расходы.
7. CSV/XLSX импортируются после preview.
8. Дубли обнаруживаются до commit.
9. Критические сценарии покрыты тестами.
10. Интерфейс удобен на телефоне и компьютере.
11. В репозитории и логах нет секретов и реальных финансовых данных.
12. Typecheck, lint, tests и build проходят.

## 20. Roadmap после первого интернет-релиза

Следующие продуктовые расширения утверждены пользователем, но реализуются отдельными обратимыми этапами:

- [реализовано 4.3] полная локализация интерфейса RU/EN с сохранением языка в профиле;
- [реализовано 4.3] шесть доступных тем и ограниченный выбор типографики;
- [реализовано 4.9] favicon/PWA-иконка из двух соединённых форм как символа общей цели;
- [реализовано 4.2/4.3] контакты разработчика/поддержки; внешняя ссылка для добровольной поддержки проекта остаётся отдельным этапом;
- мультивалютные накопления с основной валютой цели и исходными операциями в KZT, EUR, USD и RUB;
- Git-история каждого успешного изменения и release-процесс через preflight;
- production-данные продолжают жить в текущем Supabase-проекте при переходе из beta в обычный релиз.

Мультивалютность меняет прежнюю границу MVP «без конвертации валют», поэтому до её реализации схема и финансовые инварианты должны быть расширены отдельной спецификацией. Нельзя молча переиспользовать текущую одно-валютную модель. Исходная сумма и валюта операции должны сохраняться неизменно, а курс/источник/время оценки — быть проверяемыми. Финансовая математика по-прежнему не использует `float`.

## Stage 4.4 — Multi-currency savings

- Supported savings currencies: `KZT`, `EUR`, `USD`, `RUB`.
- The goal currency remains the reporting/target currency for the progress bar and target amount.
- Every savings transaction permanently stores its original `amount_minor` and `currency_code`.
- Foreign-currency savings are converted only for reporting/progress using the current official National Bank of Kazakhstan rate.
- Cross-rates between non-KZT currencies are derived through KZT using integer/rational arithmetic; money calculations must not use floating point.
- UI must show the original amount, converted equivalent, effective rate date and source when conversion is used.
- If the official rate is temporarily unavailable, foreign amounts must not be silently converted with guessed data; UI must disclose that the converted total is incomplete.
- Negative-balance protection applies per original currency.
- Expenses remain denominated in the goal currency in this stage; multi-currency expenses are out of scope.

## Stage 5.0 — Accessibility and security hardening

- Primary actions use each theme's dark accent token so white button text reaches WCAG AA contrast.
- Keyboard focus is visible on buttons, links, form fields and disclosure summaries.
- Public responses include baseline headers for HSTS, frame protection, base URI protection, MIME sniffing prevention and restrictive legacy cross-domain policies.
- This stage does not change financial behavior, stored data or the Supabase schema.

## Stage 5.1 — Manual entry confirmation

- Manual savings and expense forms must show a pending state while a write is in progress.
- The submit control must be disabled during the request to prevent accidental duplicate operations.
- After a successful write, confirmation must appear next to the submit control without requiring the user to scroll to a changed aggregate.
- Successfully submitted fields are reset for the next entry; starting a new entry dismisses the previous confirmation.
- Confirmation is announced through an accessible live status.
- This stage does not change financial calculations, stored data or the Supabase schema.
